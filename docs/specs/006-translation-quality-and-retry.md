# obs-live-translate-caption 미번역 탐지 및 재번역 스펙

작성일: 2026-09-11
대상: `001-caption-translation-pipeline.md` §4.4 번역 프롬프트·응답 처리에 품질 검사와 제한적 교정을 추가
연관 스펙: `README.md`, `001-caption-translation-pipeline.md`, `005-caption-segments-and-versioning.md`
상태: 작성 완료, 구현 미착수; 005 계약과 구현 완료 후 통합

이 문서는 `001`의 번역 요청에서 도착 언어별 지시, 고유명사 표기, 로컬 미번역 의심 탐지와
최대 1회 비동기 재번역을 분리해 다룬다. 발화 분할·SMART 수정·표시 수명·결과 반영은
`005-caption-segments-and-versioning.md`의 계약을 사용하며 별도 버전 체계를 만들지 않는다.
아래 동작은 구현 목표이며 현재 제품의 기능이나 검증된 성능을 뜻하지 않는다.

## 1. 목표와 비목표

검증 문장:

```text
일본어 자막에 한국어 원문이 그대로 남는 의심 결과는 첫 표시를 재번역 완료까지 막지 않고 최대 한 번 교정하며, 정상 고유명사는 불필요하게 재요청하지 않고 만료·구버전 응답은 표시를 덮어쓰지 않는다.
```

### 목표

| 영역 | 목표 |
|---|---|
| 예방 | 공통 번역 지시와 도착 언어 규칙을 합성하며 일본어 출력 규칙을 먼저 제공한다. |
| 표기 | STT 인식 힌트와 언어별 번역 표기 사전을 분리한다. |
| 탐지 | 원문 복사·한글 잔존·명시적 표기 위반을 로컬에서 검사한다. 의미 유사도는 사용하지 않는다. |
| 교정 | 의심도가 높은 결과만 같은 원문으로 최대 1회 재번역하고 표시 중 해당 구간을 교체한다. |
| 지연 | 기본 3개 HTTP 슬롯 안에서 교정은 최대 1개만 실행하며 일반 번역을 우선한다. |
| 관측 | 검사 시간, 판정 이유, 오탐·미탐, 교정 결과, 요청 증가량과 일반 번역 지연을 구분해 기록한다. |

## 2. 성공 기준

1. 일본어 요청은 첫 요청·문맥 없는 요청에도 공통 지시, 일본어 출력 규칙과 짧은 예시를 포함한다. `ja`와 `ja-*`는 일본어 규칙을 선택하고 다른 언어는 해당 대상 언어 이름·코드가 있는 공통 지시를 사용한다.
2. 한국어 STT 사전 `로블록스`와 일본어 표기 매핑 `로블록스 → Roblox`가 설정되면 STT setup에는 기존 인식 힌트만 들어가고 번역 요청에는 도착 언어 매핑이 들어간다. 표기 매핑을 단어 경계 없는 사후 문자열 치환으로 번역문에 적용하지 않는다.
3. 기본 fixture에서 일본어 대상의 `오늘 로블록스 할까요? → 오늘 로블록스 할까요?`는 `suspected`다. `Roblox → Roblox`, 숫자만 있는 입력, 설정으로 명시한 보존 표기는 자동 재번역하지 않는다.
4. 전체 유사도가 낮아도 `今日は로블록스で遊びます。`처럼 원문에서 온 비허용 한글이 남은 결과는 §4.3의 잔존 규칙으로 탐지한다. 단, fixture의 한글 연속 구간은 실제 원문과 정확히 대응하는 것으로 구성한다.
5. 짧은 라틴 문자 입력, 영어→프랑스어의 동일 문자열, 가나가 없는 한자·브랜드 출력은 문자 종류나 유사도만으로 실패 처리하지 않는다. 근거가 부족하면 `indeterminate`로 표시를 허용하고 자동 재번역하지 않는다.
6. 검사기는 UTF-8 입력과 빈 문자열·혼합 문자·긴 문자열을 처리하며 §4.3의 길이 상한을 지킨다. 외부 서비스·오디오 콜백을 호출하지 않는다. 의미 유사도 API는 없다.
7. `suspected` 첫 결과는 가벼운 검사 후 바로 최초 표시 후보가 된다. 교정은 실제 visible이 된 구간에 한해 예약하며, 같은 `(generation, segment_id, source_revision)`에서 최대 한 번만 실행한다.
8. 교정 성공은 `005` 계약으로 현재 visible 구간만 교체한다. 교정 중 원문 변경·설정 변경·만료·stop이 발생하면 옛 결과를 무시한다. 새 revision은 첫 시도 1로 시작한다.
9. 교정 결과가 다시 `suspected`이거나 HTTP/파싱 실패면 세 번째 요청을 만들지 않고 현재 표시를 유지한다. `indeterminate`도 자동 교체하지 않는다. 현재 세대의 401/403은 기존 `AuthError` 정지 규칙을 따른다.
10. 가짜 전송기로 전체 실행 수가 3 이하, `quality_retry` 실행 수가 1 이하임을 확인한다. 일반 큐에 작업이 있으면 새 교정은 시작하지 않는다. 활성 교정 1개 때문에 나머지 2개 슬롯까지 교정이 점유하지 않는다.
11. 교정 예약 후 만료까지 1,000ms 미만이면 dispatch하지 않는다. 교정 큐는 4개 이하이며 일반 큐가 계속 바쁘면 교정이 실행되지 않은 채 만료되는 것을 허용한다.
12. 설정 키 누락은 §4.6 기본값으로 동작한다. 잘못된 사전 JSON은 설정 오류로 표시하고 마지막 유효 사전을 유지하며 원문을 자동 삭제하지 않는다. 교정 기능을 끄면 신규 교정을 중단하고 이미 실행 중인 교정의 표시 반영도 차단한다.
13. 로그로 검사·HTTP·큐 대기를 분리하고 의심률, 재시도율, 교정 채택률, 만료 폐기 수를 산출할 수 있다. 일반 로그와 성능 결과에는 원문·번역 본문·사전 내용·인증 정보가 없다.
14. §5의 판정 fixture·스케줄러·파이프라인 통합 회귀와 전체 빌드가 exit 0이다. 로컬 검사 성능 및 실제 모델 품질은 별도로 측정하고 미측정 상태를 통과로 표기하지 않는다.

## 4. 기능 범위

### 4.1 공통 프롬프트와 일본어 규칙

프롬프트는 `공통 지시 + 도착 언어 규칙 + 표기 사전 + 짧은 예시`로 조립한다. 이전 문맥과
번역할 원문은 기존 user 입력에서 구분하며, 문맥을 번역 출력에 다시 포함하지 않도록 한다.
공통 지시는 한 곳에서 관리하고 대상 언어별 파일에 복사하지 않는다.

공통 규칙은 대상 언어로 번역문만 출력, 의미 보존, 문맥은 참고만, 짧은 자막체,
미완성 발화의 생략된 결론을 임의로 완성하지 않음이다. 입력이 이미 대상 언어이면 최소한의
정리만 허용하되 고유명사 하나라는 이유로 모든 입력을 원문 보존 대상으로 간주하지 않는다.
원문 언어는 자동 인식을 유지하며 모든 입력을 한국어라고 고정하지 않는다.

일본어 규칙은 다음을 추가한다.

- 자연스러운 일본어 자막으로 작성한다. 문장 속 고유명사도 지정한 일본어 출력 표기를 따른다.
- 지정 표기가 없으면 통용 표기·가타카나를 사용하고 관례적인 브랜드 라틴 표기는 허용한다.
- 한글로 적힌 이름이라는 이유만으로 한글 표기를 보존하지 않는다. 명시적 표기 사전 예외는
  이 규칙보다 우선한다.
- 짧은 단어와 미완성 절도 번역 대상이다. 이름·숫자를 임의로 다른 정보로 바꾸지 않는다.

기본 예시는 `로블록스 → Roblox`, `로블록스 할까요? → Robloxをやりましょうか？` 두 개를
사용한다. 해당 source에 사용자 매핑이 있으면 예시의 표기도 매핑에 맞춰 생성한다.
예시는 인식 힌트나 제품 내 자동 예외 등록을 의미하지 않는다. 첫 요청과 후속 요청의 규칙은
동일하며 모델이 세션에서 번역 규칙을 학습한다고 가정하지 않는다.

목표 언어 규칙은 `ja` 및 기본 언어 subtag가 `ja`인 코드에 적용한다. 그 외에는 공통 규칙만
쓴다. `005`에서 제거한 박스 길이 압축 힌트를 복구하지 않는다. 기존 모델 선택,
`maxOutputTokens=256`, 샘플링/thinking 파라미터 생략은 유지한다.

### 4.2 음성 인식 사전과 번역 표기 사전

기존 `caption_custom_vocabulary`는 STT 인식 힌트로 유지한다. 번역에는 이름임을 알려주는
보조 목록으로 사용할 수 있지만 원문 철자를 강제하지 않는다. 새 `caption_translation_glossary`
설정은 대상 언어별 source→target 매핑 JSON 문자열이며, JSON 객체의 키와 값은 데이터로
직렬화해 지시문과 구분한다.

```json
{"ja":{"로블록스":"Roblox","마인크래프트":"マインクラフト"}}
```

이 예시는 설정 형식 설명이며 사용자 설정의 기본값은 `{}`다. 특정 철자를 그대로 보존하려면
동일 source/target을 명시할 수 있다. 표기 우선순위는 정확한 언어 코드 매핑 → 기본 언어
매핑 → 대상 언어 일반 규칙이다. 같은 source의 충돌은 더 구체적인 언어 코드가 이긴다.

검증은 객체→언어 코드→문자열 매핑 구조, 중복 JSON 키 거부, 빈 source/target 거부,
NUL·줄바꿈 같은 제어 문자 거부를 포함한다. 전체 JSON은 UTF-8 16KiB 이하, 합계 100개
매핑 이하, 각 source/target은 80 코드 포인트 이하로 제한한다. 제한은 파싱 전/후 모두 적용한다.
설정 오류 시 유효 사전 스냅샷을 교체하지 않는다. 첫 로드에서 유효 사전이 없으면 빈 사전을
사용하고 오류를 안내한다. API 키나 다른 설정까지 거부하지 않는다.

현재 구간과 최대 3개 문맥에 실제 등장한 항목만 길이 내에서 프롬프트에 포함한다.
source 매칭은 최장 일치 우선이며 라틴 단어는 문자/숫자 경계를 확인한다(`Rob`을
`Roblox` 안에서 매칭하지 않는다). 한글 조사는 이름 뒤에 붙을 수 있으므로 이름 자체를
매칭하되 뒤의 조사·일반 문장까지 허용 예외로 마스킹하지 않는다. 사용자 사전 값으로
번역문을 강제 치환하지 않고 모델 입력과 검증 기준으로 사용한다.

### 4.3 로컬 판정

결과는 번역의 의미적 정답 판정이 아닌 아래의 운영 분류다.

| 결과 | 의미 | 자동 동작 |
|---|---|---|
| `normal` | 검사 범위에서 강한 미번역 신호가 없거나 명시적 허용 예외다. 정확한 번역임을 보장하지 않는다. | 표시 허용 |
| `suspected` | 적용 가능한 언어 규칙 또는 표기 규칙을 위반하는 강한 신호가 있다. | 첫 결과 표시 허용, 조건 충족 시 교정 후보 |
| `indeterminate` | 짧거나 모호하거나 지원하지 않는 언어쌍이라 판정 근거가 부족하다. | 표시 허용, 자동 교정 없음 |

검사는 작업 스냅샷의 대상 언어·원문·표기 사전으로 수행한다. 최신 설정을 중간에 섞지 않는다.
UTF-8을 코드 포인트로 읽고 공백 정리, 비교용 문장부호 제거, ASCII 대소문자 접기만 수행한다.
숫자·문자·한글 자모는 보존하며 가독성 있는 원문 자체는 수정하지 않는다. 유니코드 전 범위의
정규화나 완전한 언어 판별을 구현했다고 표현하지 않는다.

1. API/파싱 오류나 빈 결과는 기존 번역 실패 경로다. 품질 교정을 생성하지 않는다.
2. 전체 입력과 출력이 같은 숫자·기호·URL 또는 명시적으로 허용한 표기만으로 구성되면
   `normal`이다. 사전 항목이 포함됐다는 이유로 문장 전체를 예외 처리하지 않는다.
3. 일본어 대상에서는 명시적으로 허용한 한글 표기 부분을 제외한 뒤 다음을 검사한다.
   원문 한글이 2개 이상이고 비교용 원문/출력이 같으면 `suspected: source_copy`다.
   출력에 원문에서 그대로 가져온 비허용 한글 연속 구간이 4개 이상이면
   `suspected: hangul_residue`다. 완성형 한글과 자모 블록을 포함한다.
4. 매핑이 있는 source 철자가 결과에 그대로 남고 지정 target이 그 위치에 반영되지 않은
   경우 `suspected: glossary_mismatch`로 분류한다. target이 없다는 이유만으로 source까지
   없는 결과를 실패시키지 않는다. 위치 대응이 모호하면 `indeterminate`다.
5. 위 조건으로 판정하지 못한 후보에 한해 문자열 유사도를 보조 계산한다.
   `similarity = 1 - edit_distance / max(source_length, output_length)`를 사용한다.
   두 길이가 모두 0이면 예외로 처리하며, 각 문자열이 256 코드 포인트 이하일 때만
   두 행 DP로 계산한다. 일반 문자가 8개 이상이고 유사도 0.90 이상이며 일본어 출력에
   원문에서 온 비허용 한글이 2개 이상 남으면 `suspected: near_copy`다.
6. 일본어의 가나가 없다는 사실, 원문/출력이 라틴 문자라는 사실, 유사도 단독으로는
   `suspected`가 되지 않는다. 한글 없는 짧은 동일 이름(`Roblox`, `OK`)은 별도 매핑이
   없으면 `indeterminate`이고 자동 교정하지 않는다. 나머지 지원 범위의 일본어 출력은
   `normal`, 일반 fallback 언어는 명시적 사전 위반 외에는 `indeterminate`다.

유사도 0.90 등의 수치는 초기 정책이며 §5의 라벨 fixture로 조정한다. 의미 임베딩 유사도는
정상 번역도 높게 나와 미번역 판단 근거가 아니므로 사용하지 않는다. 256 코드 포인트 초과는
유사도만 생략하고 선형 시간 문자/사전 검사는 `005`의 입력 상한 안에서 계속 수행한다.
정규식 catastrophic backtracking이 가능한 패턴이나 무제한 부분 문자열 DP는 사용하지 않는다.

한글 1–3자의 부분 잔존, 동의어 오역, 문장 일부의 누락은 탐지하지 못할 수 있다. 인용문에서
한글을 보존해야 하는 경우도 오탐이 가능하며 필요한 표기를 명시적 사전으로 허용한다.
이 한계를 정확도 지표에서 숨기지 않는다.

### 4.4 교정 요청과 버전

동기 로컬 검사 후 첫 응답은 정상 표시 흐름에 넣는다. `suspected`이면 사유만 붙여 두고,
실제로 그 구간이 화면에 들어온 때 교정 예약 조건을 평가한다. 기다리는 구간을 교정하느라
최초 표시를 늦추지 않는다. 짧은 페이지는 교정이 끝나기 전에 지나갈 수 있다.

교정은 `005`의 동일 `generation`, `utterance_id`, `segment_id`, `source_revision`으로
`attempt_id=2`, `request_kind=quality_retry`를 사용한다. 첫 요청과 동일 원문·문맥·모델·언어·
사전 스냅샷에 판정 사유별 짧은 추가 지시만 붙인다. 이전 오답 번역을 원문 대신 번역하지 않는다.

- `source_copy`/`near_copy`/`hangul_residue`: 대상 언어로 원문을 새로 번역하고 비허용 원문
  철자를 그대로 출력하지 않도록 지시한다. 이름은 허용한 표기를 따른다.
- `glossary_mismatch`: 적용할 source→target 매핑을 강조한다.

한 원문 버전에서 교정 시작은 최대 1회다. 예약 중복은 하나로 합치며 queue 퇴출·기능 해제·
만료 뒤 동일 버전으로 반복 예약하지 않는다. 교정 결과를 같은 로컬 검사로 확인하고
`normal`인 경우에만 표시 중 구간에 반영한다. `suspected`/`indeterminate`/오류면 현재 번역을
유지하고 종료한다. 품질 실패를 원래 구간의 `on_failed`처럼 처리해 자막을 지우지 않는다.

교정 예약에는 당시 표시 페이지의 토큰과 만료 시각도 저장한다. 같은 세그먼트라도 다음
페이지로 넘어갔으면 이 교정 결과를 폐기한다. 별도 요청 버전 체계가 아니라 표시 수명
검사에 필요한 스냅샷이며, 결과 수락 시 페이지 토큰까지 원자적으로 확인한다.

SMART 원문 v3이 생기면 v2 교정은 무효다. v3은 원문이 다른 새 일반 번역이며 시도 1과
독립적인 1회 교정 예산을 갖는다. 원문 수정이 반복되어도 `005`의 작업 합치기·전체 수명·
큐 상한으로 제한한다. 결과 수락과 visible 확인은 동일 상태 전이에서 처리한다.

### 4.5 3개 슬롯 안의 우선순위와 만료

| 항목 | 결정 |
|---|---|
| 전체 실행 HTTP | 최대 3개, `005`와 동일 풀 |
| 품질 교정 실행 | 최대 1개. 별도 워커를 늘리지 않는다. |
| dispatch 우선순위 | `005`의 최초/원문 수정 작업을 먼저 선택한다. 일반 큐가 비고 슬롯이 남을 때만 교정 1개를 시작한다. |
| 교정 예약 큐 | 최대 4개이며 `005`의 전체 시작 전 작업 12개 상한에도 포함된다. 동일 버전 중복은 합친다. |
| 예약·시작 조건 | 현재 visible이며 최신 원문 버전이고 기능이 켜져 있으며 현재 페이지 만료까지 1,000ms 이상 남아 있어야 한다. |
| 만료 기한 | 예약 당시 페이지 만료 시각과 현재 페이지 만료 시각 중 이른 시각. 페이지 전환으로 기한을 연장하지 않는다. |
| 교정 타임아웃 | 남은 유효 시간 이내의 전체 요청 deadline을 적용하고 기존 연결·전송 제한보다 길게 잡지 않는다. |
| 과부하 | 일반 작업 때문에 전체 큐 한도에 도달하면 교정 예약부터 제거한다. 교정 큐가 가득 차면 새 후보를 생략한다. |

교정이 이미 실행 중일 때 새 일반 작업이 오면 나머지 슬롯으로 시작한다. 실행 중 교정을
논리적으로 취소해도 실제 HTTP 완료 전에는 슬롯이 빈 것으로 계산하지 않는다. 클라이언트가
정밀 deadline 취소를 지원하지 않으면 스케줄러에서 기한 경과 결과를 버리고 실제 요청은
기존 타임아웃 안에서 끝나도록 한다. 이 경우 네트워크 점유 지연을 따로 기록한다.

따라서 교정이 일반 번역에 전혀 영향을 주지 않는다고 보장하지 않는다. 일반 부하가 크면
교정이 한 번도 시작하지 않아도 정상 정책이다. HTTP 429·5xx·타임아웃은 품질 재시도 연쇄를
만들지 않으며 HTTP 401/403은 현재 세대인 경우에만 세션을 멈춘다.

### 4.6 설정·로그

| 키 | 타입·기본값 | 의미 |
|---|---|---|
| `caption_quality_retry` | bool, `true` | 로컬 의심 탐지에 따른 자동 교정을 허용한다. 꺼도 검사·계측과 언어별 프롬프트는 유지한다. |
| `caption_translation_glossary` | string, `"{}"` | §4.2의 언어별 표기 매핑 JSON. 고급 설정 및 `SetSourceFilterSettings`로 입력한다. |

UI는 “미번역 의심 시 한 번 재번역” / “Retry suspected untranslated captions once” 체크박스와
“번역 표기 사전 (JSON)” / “Translation glossary (JSON)” 입력 및 형식 오류 안내를 제공한다.
검사 임계값·워커 수를 일반 UI에 노출하지 않는다. 한국어·영어 locale과 두 README를 갱신한다.

유효한 표기 사전/대상 언어/모델 변경은 `005`의 세대 변경으로 기존 작업을 무효화한다.
`caption_quality_retry=false`는 일반 번역 세대를 바꾸거나 자막을 지우지 않고 교정 작업만
예약 취소·논리 무효화한다. 다시 켜도 같은 버전에서 이미 소모/종료한 교정을 되살리지 않는다.

로그는 식별자, 원문/출력 코드 포인트 수, 적용 규칙, 판정, `detect_us`, 유사도 또는 생략 사유,
`retry_queue_ms`, `retry_http_ms`, `retry_outcome`만 기록한다. 결과 사유는 최소
`accepted`, `still_suspected`, `indeterminate`, `expired`, `superseded`, `disabled`,
`queue_full`, `http_failure`를 구분한다. 지표 분모는 검사한 첫 번역 수·예약한 교정 수·실행한
교정 수를 각각 보관해 혼동하지 않는다. 품질 판정의 오탐률은 사람이 라벨한 평가 데이터로만
계산하며 런타임 `normal` 수를 정답률로 표현하지 않는다.

`finishReason=MAX_TOKENS` 등의 생성 중단은 미번역과 다른 원인이다. 구현 시 응답에 존재하면
진단 사유로 보존하고 해당 결과를 품질 교정 대상으로 삼지 않는다. 출력 토큰 상한 조정·
이어쓰기 복구는 이 스펙의 범위에 포함하지 않는다. 본문이 있는 부분 응답의 기존 표시 여부는
유지하되 로그에서 정상 종료와 구분한다.

## 5. 검증 방법

아래는 **구현 후 검증 계획**이다. 신규 타깃과 fixture는 아직 존재하지 않으며 스펙 작성으로
테스트가 통과한 것으로 취급하지 않는다. 005와 같은 CMake/VS 준비 조건을 적용한다.

```bash
# 기준 14: 설정. VS 2022는 windows-x64 프리셋 사용
cmake --preset windows-x64-vs2026
# 기준 1–6·12: 신규 사전/판정 모듈 + 기존 프로토콜 테스트
cmake --build --preset windows-x64-vs2026 --target translation-glossary translation-quality translate-protocol
ctest --test-dir build_x64 -C RelWithDebInfo -R '^(translation-glossary|translation-quality|translate-protocol)/' --no-tests=error --output-on-failure
# 기준 7–13: 005 모듈에 추가되는 교정 스케줄링·가짜 전송 테스트
cmake --build --preset windows-x64-vs2026 --target translation-scheduler caption-pipeline
ctest --test-dir build_x64 -C RelWithDebInfo -R '^(translation-scheduler|caption-pipeline)/' --no-tests=error --output-on-failure
# 기준 14: 전체 플러그인 및 회귀
cmake --build --preset windows-x64-vs2026
ctest --test-dir build_x64 -C RelWithDebInfo --no-tests=error --output-on-failure
# 기준 6·13–14: S2에서 추가할 수동 성능 테스트. 일반 CTest에는 숨김
./build_x64/tests/RelWithDebInfo/translation-quality.exe '[.quality-perf]'
```

- 기준 3–6: fixture는 단어 단독, 브랜드만, 숫자·URL, 완전 원문 복사, 부분 한글 잔존,
  한자만 있는 일본어, 혼합 언어, 한국어 인용, 라틴 언어 간 유사 문장, 사전 보존 예외,
  UTF-8 자모·전각·결합 문자와 256 코드 포인트 경계 양쪽을 포함한다. 최소 40개 판정
  fixture에 기대 분류와 이유를 명시하고 세 규칙의 복사·잔존·사전 위반을 각각 검증한다.
- 기준 7–11: 첫 응답 표시 전에 두 번째 HTTP를 기다리지 않는지, 일반 3개 실행 중 교정이
  시작하지 않는지, 일반 2개+교정 1개에서 추가 교정이 시작하지 않는지 barrier로 검사한다.
  visible 진입·만료 직전/정확한 경계, 교정 실패, 결과 역전, SMART revision 변경,
  기능 OFF→ON, 설정 변경과 stop을 가짜 시계·전송기로 재생한다.
- 로컬 성능: Release 계열 빌드에서 고정 fixture를 warm-up 후 10,000회 검사하고 p50/p95/max,
  CPU·빌드·문자열 길이를 출력한다. 일반 자막(양쪽 256 코드 포인트 이하)의 `detect_us`
  p95 1,000µs 이하를 초기 목표로 둔다. 이는 아직 측정하지 않은 목표이며 환경에 민감한
  절대 시간 assertion으로 일반 CI를 실패시키지 않는다. 넘으면 일반 부하 측정 전에 원인을
  분석하고 결과를 문서에 남긴다.
- 실제 모델 평가: 비민감·수동 라벨 원문 최소 40개를 사용해 ① 기존 프롬프트 ② 언어 규칙만
  ③ 언어 규칙+탐지·교정을 비교한다. 각 조건에서 같은 문장당 3회 요청하고 시작 직후
  문맥 없음과 이전 3개 구간 문맥을 구분한다. 1차 비교와 이후 튜닝 평가 표본을 분리한다.
  요청 수·모델·실행 시각·미번역률·오탐/미탐·교정 채택/실제 개선률을 기록한다.
- 부하/OBS 평가: 같은 음성의 연속 발화 60초 이상에서 교정 OFF/ON 각 1회로 일반 번역
  큐 대기와 최초 표시 p50/p95, 총 HTTP 수, 교정 만료율을 비교한다. 늦은 교정이 자막을
  부활시키지 않는지, 동일 소스 설정에서 한국어 원문이 번역 소스를 덮어쓰지 않는지도 확인한다.
- API 평가와 OBS 확인은 해당 환경이 준비되었을 때 수행한다. 문서 작성 단계에서 유료
  요청을 실행하지 않으며 구현 테스트 통과와 실제 모델 품질·성능 검증을 분리해 보고한다.
